# Planner Service

Planner — HTN‑движок, который строит, обновляет и ранжирует планы для целей.
Сервис реализован как воркер: он подписывается на запросы оркестратора, строит
дерево задач и генерирует контракты для ролевых агентов.

## Что входит в репозиторий
- `planner/worker.py` — точка входа. Здесь же появится цикл обработки событий.
- `planner/engine/` — место для HTN‑ядра: методы, эвристики, табу‑списки.
- `planner/methods/` — каталог доменных методов разложения задач.
- `planner/policies/` — стратегии выбора ролей и бюджетов.
- `planner/adapters/` — соединение с NATS/Postgres/Redis.
- `planner/domain/` — общие типы плана: узлы, статусы, эвристики.

## Потоки данных
1. Оркестратор публикует запрос `plan.request` в NATS.
2. Planner считывает запрос, ищет подходящие HTN‑методы и строит дерево.
3. Результат сохраняется в Postgres, публикуется событие `plan.ready`.
4. Contract Manager превращает дерево в контракты и выдает воркерам.

## Конфигурация (ожидаемая)
| Переменная | Назначение |
|------------|------------|
| `DATABASE_URL` | Источник данных о целях, шаблонах и статусах. |
| `NATS_URL` | Очередь событий `plan.*`. |
| `REDIS_URL` | Кэш для эвристик и блокировок. |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Экспорт трейсов планирования. |
| `PLAN_MAX_DEPTH`, `PLAN_MAX_BREADTH` | Ограничения на размер плана (опционально). |

В `docker-compose.yml` переменные уже определены для локального окружения.

## Как запускать локально
```bash
cd apps/planner
poetry install  # или pip install -r requirements.txt
python -m planner.worker
```

Для отладки включите `LOG_LEVEL=DEBUG` и подключите `NATS_URL` к локальной
шине (поднимается командой `make up`).

## Тестирование
Планируется использование `pytest` + property‑tests для методов. Добавляйте
фикстуры в `tests/` (например, `tests/planner/`). Важно проверять, что методы
возвращают валидные контракты и соблюдают ограничения SLA.
