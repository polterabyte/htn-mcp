## 1. Введение
Система предназначена для иерархической декомпозиции задач с помощью HTN-планирования (Hierarchical Task Networks).  
Ключевая идея — сущности-агенты, которые способны:
- Разбивать цель на подзадачи.
- Назначать дочерних агентов с ограниченными ресурсами.
- Выполнять или делегировать задачи.
- Использовать фиксированный набор инструментов.

---

## 2. Основные компоненты

### 2.1 Root Agent (Координатор)
- Получает глобальную задачу и ресурсы (бюджет, дедлайн, глубину).
- Запускает HTN-планировщик для декомпозиции цели.
- Распределяет подзадачи по ролям.

### 2.2 HTN Planner
- Методы разложения описывают, как цель можно разбить на подцели.
- Поддерживает несколько методов для одной цели.
- Выбор метода учитывает роль агента и доступные ресурсы.

### 2.3 Subtasks и Contracts
- Каждая подзадача оформляется в **контракт**:
  - Цель и параметры.
  - SLA: бюджет, дедлайн, глубина.
  - Ожидаемые факты/результаты.
  - Критерии успеха.

### 2.4 Child Agents
- Получают контракты от родителя.
- Имеют разные **роли**:
  - **Аналитик** — декомпозирует задачи.
  - **Исполнитель** — предпочитает инструменты.
  - **Верификатор** — проверяет результаты.
  - **Координатор** — управляет другими агентами.


### 2.5 MCP Servers (Инструменты)
_Регистрацию и эксплуатацию MCP‑серверов см. в_ **[TOOLS.md](TOOLS.md)**.

В этой системе **инструменты = MCP-сервера** (Model Context Protocol). Каждый инструмент — это удалённый сервер, предоставляющий набор операций (tools) через MCP.

**Что регистрируем в реестре:**
- `server_id`, `version`
- Транспорт: `stdio` или `http`
- Конечная точка/команда запуска (для stdio) или URL (для http)
- Каталог операций (результат `tools.list`) с JSON-схемами входов/выходов
- Лимиты: concurrency, rate limit, максимальный размер payload
- Стоимость/вес: локальная модель ценообразования для планировщика (эвристика)
- Политики надёжности: таймауты, ретраи, circuit breaker

**Жизненный цикл вызова MCP-инструмента:**
1) **Discovery:** при регистрации или лениво — `tools.list` и кеширование схем в реестре.
2) **Validation:** сопоставление параметров подзадачи с JSON-схемой операции.
3) **Budget & SLA check:** прогнозируем время/стоимость и сверяем с контрактом.
4) **Invocation:** JSON-RPC вызов операции; транспорт — `stdio` (процесс) или `http`.
5) **Postconditions:** верификация выходов по схеме и инвариантам контракта.
6) **Write-back:** запись результатов в Blackboard с idempotency ключом (`server_id:tool:inputs_hash`).

**Адресация инструмента в плане:** `mcp://{server_id}/{tool_name}@{version}`

**Ошибки MCP маппятся на статусы контракта:**
- `timeout` → `Failed.Timeout`
- `rate_limited`/`unavailable` → `Failed.Budget|Backpressure` (в зависимости от политики)
- `invalid_params` → `Failed.InvariantBreach` (ошибка на стадии валидации)
- `internal_error` → реплан + `circuit_breaker` инкремент

### 2.6 Blackboard (Общий контекст)
- Идемпотентные записи для MCP-вызовов по `inputs_hash`.
- Теги источника: `server_id`, `tool`, `contract_id`.

- Хранилище фактов и результатов.
- Общедоступно для агентов разных уровней.
- Используется верификатором для проверки выполнения контрактов.

## 3. Ограничения ресурсов
- Родительский агент распределяет ресурсы между поддеревьями.
- Ограничения включают:
  - Суб-бюджет (стоимость инструментов).
  - Суб-дедлайн (тайм-аут).
  - Глубину рекурсии.
  - Лимит числа помощников.

---

## 4. Контракты между агентами
_Подробнее про формат и политику см. в_ **[CONTRACTS.md](CONTRACTS.md)**.

- Контракт задаёт формальные отношения между родителем и дочерним агентом.
- Родитель гарантирует ресурсы и контекст.
- Дочерний агент обязуется:
  - Выполнить задачу в рамках SLA.
  - Сообщить о сбое или невозможности.
- Контракты фиксируются в журнале для трассируемости.

---

## 5. Жизненный цикл задачи
1. Root Agent получает глобальную цель.  
2. Запускается HTN-планировщик → строится сеть задач.  
3. Задачи превращаются в контракты.  
4. Контракты распределяются между Child Agents с ролями.  
5. Child Agents используют инструменты или снова раскладывают задачи.  
6. Результаты пишутся в Blackboard.  
7. Верификатор сверяет результаты с условиями контрактов.  
8. Root Agent принимает решение об успехе или повторной декомпозиции.

---

## 6. Поведение при сбоях
- **Нарушение SLA**: задача отклоняется, выбирается альтернативный метод.  
- **Дефицит ресурсов**: агент отклоняет контракт (fail-fast).  
- **Циклы**: детектор циклов по хэшу (goal + params).  
- **Неудача поддерева**: эскалация на уровень выше, пересмотр декомпозиции.

## Приложение A: Интеграция с MCP-серверами

### A.1 Реестр MCP
- **Warm pool**: для `stdio`‑серверов поддерживается пул живых процессов (min/max), чтобы уменьшить холодный старт.
- **Health/Heartbeat**: периодические пробы (`ping`/no-op) с экспоненциальным backoff; деградация при сбоях.
- **Версионирование**: одновременная поддержка нескольких версий сервера, выбор по совместимости схем.

### A.2 Контракты и MCP
Контракт подзадачи расширяется полем `mcp_policy`:
```yaml
mcp_policy:
  allow: ["mcp://img-gen/resize@^2", "mcp://db/query@>=1 <3"]
  deny: ["mcp://net/*"]
  transport: ["stdio"]           # опционально: фиксируем транспорт
  timeouts: {connect_ms: 2000, call_ms: 15000}
  retries: {max: 1, backoff_ms: 500}
  concurrency: 2                 # локальная квота для контракта
```
Верификатор проверяет, что дочерний агент вызывал **только** разрешённые операции в пределах квот.

### A.3 Безопасность
- **Изоляция**: `stdio`‑серверы запускаются в контейнерах/сандбоксах с seccomp/AppArmor и ограничениями CPU/IO.
- **Секреты**: доступ к токенам только через секрет-хранилище и явные капабилити в контракте.
- **Сетевые политики**: deny‑by‑default; для `http` включения — адреса в allowlist.

### A.4 Наблюдаемость
- Спаны: `mcp.connect`, `mcp.call`; метрики `p50/p95`, `error_rate`, `warm_pool_hits`.
- Журналы включают: `server_id`, `tool`, `request_id`, `payload_size`, `duration_ms`, `status`.
- Для воспроизводимости сохраняем входные параметры (с редактированием секретов) и хэш ответа.

### A.5 Планирование и стоимость
- Стоимость операции = `base_cost(server, tool) * size_factor + penalty(latency)`.
- Планировщик предпочитает локальные/быстрые серверы при равной функциональности.
- Табу-лист методов/серверов при недавних сбоях → реплан на альтернативы.

### A.6 Обработка частичных результатов
- Если MCP‑операция потоковая, дочерний агент публикует чанки в Blackboard (`key@v+1`), что позволяет раннее агрегирование.
- Контракты могут требовать **минимальный объём** частичных результатов до дедлайна (graceful degradation).
